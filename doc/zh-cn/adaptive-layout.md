# 自适应布局

MyDay!!!!! 如何决定平板、桌面窗口或展开的折叠屏设备多出来的空间该拿来做什么——以及同样重要的，何时决定什么都不做。

本页的每一个数字在代码中只存在于一处：`lib/shared/utils/adaptive_layout.dart`。该模块不从 Flutter 引入任何东西，因此每条规则都是纯函数，可以在毫秒级内于五十个视口上验证（`test/adaptive_layout_test.dart`）。**如果某个 widget 文件里出现了数值宽度比较，那就是 bug**——数字属于这个模块，页面调用具名谓词。

这套约定与本系列的兄弟应用共享；它们所依据的可移植说明是与各仓库并列存放的 `ADAPTIVE-LAYOUT-GUIDE.md`。

## 三条规则

三个独立的问题对应三条独立的规则，没有任何一条经由另一条转发：

| 问题 | 规则 | 测量对象 |
|---|---|---|
| 这个布局可以分栏吗？ | `canSplitLayout(width, height)` | 整个屏幕的**形状** |
| 导航放在哪里？ | `useNavigationRail(screenWidth)` | **仅宽度** |
| 能放下几个？ | `columnCapacity(contentWidth, minItemWidth: …)` | **内容框**宽度 |

## 规则 A——布局何时可以分栏？

```dart
const splitMinWidth  = 600.0;  // Material medium width class; Android sw600dp
const splitMinHeight = 480.0;  // compact/medium height boundary
const splitMinAspect = 0.82;   // width / height
```

三个条件必须同时成立。任何一个单独都不够。

### 宽高比测试是承重的那一条

这就是为什么这条规则**不是**单纯的宽度断点，而它的存在源于一台设备。

Galaxy Z Fold 8 展开后是一块 **4:3 横向**面板（2448 x 1848 px）。竖持时它是 3:4——*相对高度比它所取代的近方形 Fold 7 更窄*，尽管它更新。Fold 8 Ultra 则走向了另一边。同一代设备展开后大致跨越 672 – 954 逻辑像素，而**同一台设备在同一个宽度上需要两个不同的答案**。没有任何宽度阈值能做到这一点；宽高比测试可以。

像素数是权威的。逻辑像素取决于密度分档以及三星可由用户调节的*显示尺寸*设置，因此 dp 数值应当视为区间。

| 设备 | 内屏面板，px | 竖持 W:H | 竖持 W，dp | 竖持 | 横持 |
|---|---|---|---|---|---|
| Galaxy Z Fold 5 | 1812 x 2176 | 0.83 | 659–690 | 分栏 | 分栏 |
| Galaxy Z Fold 6 | 1856 x 2160 | 0.86 | 675–707 | 分栏 | 分栏 |
| **Galaxy Z Fold 8** | **2448 x 1848（4:3 横向）** | **0.755** | **672–704** | **单栏** | **分栏** |
| Galaxy Z Fold 7 | 1968 x 2184 | 0.90 | 716–750 | 分栏 | 分栏 |
| Galaxy Z Fold 8 Ultra | 2256 x 2504 | 0.90 | 820–859 | 分栏 | 分栏 |
| Pixel 9 / 10 Pro Fold | 2076 x 2152 | 0.96 | 755–791 | 分栏 | 分栏 |

`0.82` 位于 Fold 8 的 `0.755` 与 Fold 7 / Ultra 的 `0.90` 之间空隙的中部附近——两侧各有约 9% 的余量。改动这个常量是全应用范围的行为变更。

### 宽度下限

即使在密度较高的一端，每一块展开面板也至少高出 600 dp 约 59 dp；而每一块折叠状态的外屏都远低于它（Fold 7 / Ultra 约 360 dp，Fold 8 约 356–416 dp，Pixel 10 Pro Fold 约 411 dp）。这条下限在不点名任何设备的前提下把「展开」和「外屏」分开。

### 高度下限

单靠宽高比测试会放行**又宽又矮**的视口。没有这条下限，折叠状态的 Fold 8 外屏横持（约 657 x 416 dp）和普通手机横持（约 915 x 412 dp）都会被分成两个逼仄的窗格。Google 的指南独立地给出了同样的结论：手机或展开的翻盖机横持时宽度属于 medium 但高度属于 compact，双窗格布局在那里并不实用。

### 事先接受的代价

这条规则关乎**形状，而不是设备类别**。4:3 平板竖持（768 x 1024 → 0.75）和 16:10 平板竖持（0.625）都保持单栏，和 Fold 8 竖持完全一样。两者横持时都会分栏。如果有人报告「我的平板竖持时不分栏」，那正是规则在正常工作。

## 规则 B——导航放在哪里？（仅宽度）

```dart
const navRailMinWidth = 600.0;
const navRailWidth    = 81.0;  // 80 dp NavigationRail + 1 dp VerticalDivider
```

`useNavigationRail` **刻意只看宽度，并且不经由 `canSplitLayout` 转发。** 导航栏不是分栏。它拿宽度——在该测试通过时是充裕的——去换高度，而高度并不充裕。它帮助最大的恰恰是分栏规则拒绝的那种情况：手机横持在 915 x 412，底部导航栏花掉 19% 的高度，而 915 dp 的宽度闲置。

`ShellScaffold`（`lib/shared/widgets/shell_scaffold.dart`）从**同一份目的地列表**构建导航栏和底部导航栏，因此一个目的地不可能只出现在其中之一，也不可能在两者之间顺序不同——包括亲密模块的目的地，当该模块被隐藏时它在这唯一的一处被过滤掉。导航栏设置 `groupAlignment: 0`：默认的顶部对齐是给位于前导菜单按钮或 FAB 之下的导航栏用的，而 MyDay 两者都没有，因此顶部对齐会让高导航栏的整个下半部分空着。它被包在 `SingleChildScrollView` + `ConstrainedBox(minHeight:)` 里，因为导航栏可能出现在高度紧凑的窗口上（915 x 412），那里它必须滚动而不是溢出。

外壳内的页面用 `shellContentWidth(screenWidth)` 计算容量，它恰好在导航栏显示时扣除导航栏宽度。**压在外壳之上的页面**——所有用 `Navigator.push` 到达的页面——没有导航栏可扣；它们测量自己的 `LayoutBuilder` 约束，且不得调用 `shellContentWidth`。

刻意没有做：在 1240 dp 以上使用 `NavigationDrawer`。导航栏一直到 extra-large 都是正确的，第三种导航模式不值得它的代价。

## 规则 C——能放下几个？（自适应最小宽度）

`columnCapacity` 问的是给定最小宽度的列在一个内容框里能放下几个，而不是为每个断点写死一个数量。分子里加了一个间隙，这样算式支付的是列**之间**的间隙，而不是每列之后各一个。

每个调用方带来自己内容所需的最小值，常量的文档注释说明这个数字从何而来。

`listColumnCount` 为可由用户固定的列数把闸门和容量结合起来，并且对存储的偏好**做钳制而不是拒绝**。正是这一点让在桌面上选定的偏好能在被带到折叠状态的手机上后幸存，并在展开时回来。设置它的控件（`lib/shared/widgets/adaptive_tile_grid.dart` 中的 `listColumnsButton`）在容量为 1 时是**隐藏**而非禁用的，因此它永远不会出现在手机或外屏上。该偏好存放在 `storage_config.json` 中，那是设备本地且从不同步的——窗口尺寸是设备的属性，不是账户的属性。

## 闸门量屏幕，容量量内容框

这种不对称是刻意的，而且很容易搞错。

- **闸门**（`canSplitLayout`、`useNavigationRail`）读 `MediaQuery.sizeOf(context)`——整个屏幕。若拿 `Scaffold` body 来衡量分栏决策，会从高度里扣掉 app bar 从而抬高比值，把竖持的 Fold 8 读成 0.80 而不是 0.755，几乎不给阈值留下余量。
- **容量和窗格宽度**读内容实际拿到的东西：`shellContentWidth(screenWidth)` 减去页面自己的内边距，或者 `LayoutBuilder` 的 `constraints.maxWidth`。

闸门问的是窗口的*形状*，导航栏不改变它。容量问的是还剩多少空间，导航栏非常明确地改变它。

## 规则 D——页面拿不能分栏的宽度做什么

不是每个页面都有两样东西可以并排。表单页或散文页只有一列内容，把它横跨桌面窗口拉伸只会更糟而不是更好：1400 逻辑像素宽的 `ListTile` 把标题和尾部控件放在屏幕两端，而那么长的一行散文要靠转头来读。

这些页面改为通过 `AdaptiveContentWidth` 设上限并居中：

| 上限 | 取值 | 适用于 |
|---|---|---|
| `formMaxContentWidth` | 720 | 备份、WebDAV、身体、伴侣与玩具管理列表、订阅 |
| `readingMaxContentWidth` | 840 | 许可证、隐私政策、玩具成本总览 |
| `dialogMaxContentWidth` | 640 | 所有表单对话框，经由 `Dialog.insetPadding` |

这是**仅看宽度且没有闸门**的，这正是关键：比自己上限更窄的页面在任何视口上都不受影响，因此手机渲染的东西不可能改变。散文比表单获得更多空间，因为它没有需要靠近彼此的控件；对话框比两者都少，因为它本来就是聚焦的单一用途界面。

包裹**可滚动组件**而不是它的子组件，这样滚动条和滚动手势仍然横跨整个窗口。对话框测量的是**屏幕**而不是它背后的页面，因为它绘制在根 overlay 上，也盖住了导航栏。

## 刻意记录的偏离

1. **没有 `shellListBottomInset`。** 指南让外壳页面在导航栏出现时去掉底部导航栏的预留空间。MyDay 的 `Scaffold` 没有设置 `extendBody`，因此 body 本就止于底部导航栏之上——外壳页面中的 `SizedBox(height: 80)` 是给 **FAB 让位**的，而 FAB 在两种模式下都停在右下角。两种情况下 80 都是正确的，一个从不变化的具名常量将是一个无话可说的数字。
2. **存储的列数偏好只属于外壳自己的列表界面。** 压在外壳之上的页面使用自动容量，不带存储偏好也不带列数按钮，这样设置界面不会为每个子页面长出一个控件。

3. **任务分区保持单列图块。** `TaskSectionWidget` 包着一个 shrink-wrap 的 `ReorderableListView`，把任务在同一分区的不同列之间拖动没有意义。因此待办页的列数规则数的是**每行的分区数**而不是每行的图块数，而它的 `taskSectionMaxColumns` 是 3，因为一共只有三个分区可以发牌。
4. **体重页的摘要/图表分栏有三重闸门，而不是两重。** 形状规则和宽度下限是指南的双重闸门；第三个条件——至少有两条记录——之所以存在，是因为低于两条时图表什么都不渲染，而一张摘要卡片孤零零地待在 280 的窗格里、旁边是一片空白，比它所要取代的堆叠布局更糟。
## 刻意声明的、与 Google 指南的偏离

Google 的自适应布局指南称窗口尺寸类别「明确不由设备屏幕尺寸决定」，且「不打算用于 *isTablet* 之类的逻辑」，并指导应用依据可用宽度而不是宽高比来决策。

本约定**刻意只在一点上偏离：宽高比测试。** 这不是疏忽。单靠宽度无法让 Fold 8 在两种朝向上得到两个不同的答案，而那个行为——横持分栏、竖持单栏——正是这条规则存在要满足的需求。

其余一切完全遵循 Google：宽度和高度下限就是它的断点，列容量就是它对信息流的指导，medium 宽度及以上使用导航栏则是它的原样建议。

## 运行时的折叠与展开

`android/app/src/main/AndroidManifest.xml` 在 activity 的 `configChanges` 中声明了 `screenLayout|screenSize|smallestScreenSize|density`（以及其他项）。窗口于是**不重启 activity** 就完成缩放，因此所有读 `MediaQuery.sizeOf` 的地方都会在下一帧重新求值。这就是「设备展开时自动切换」所需的全部——没有生命周期工作，没有需要保存和恢复的状态。没有它，activity 会被重建，任何未持久化的页面状态都会在折叠过程中丢失。参见 [platform-notes.md](platform-notes.md)。

## 测试

1. **纯函数测试**（`test/adaptive_layout_test.dart`）：每个阈值在 `n - 1` 和 `n` 处、每个钳制在两端、以及跨区间的不变量循环断言。每个视口都点名它所代表的真实设备，这样回归报告的是它会弄坏的设备，而不是一个光秃秃的数字。
2. **组件测试**在同样的几何尺寸下针对渲染后的页面进行（`test/shell_nav_ui_test.dart` 以及各页面的布局测试）：断言相对位置（相同的 `y`、不同的 `x`）而不是绝对像素，并且始终 `expect(tester.takeException(), isNull)` 以捕获溢出条纹。
3. 组件测试中有两点会咬人：
   - **`flutter_test` 把它默认字体的每个字形都渲染成一个完整的全角方块**，把拉丁标签撑大到实际宽度的约 2.5 倍，因此布局测试可能在生产中完全宽裕的宽度上报告溢出。因此布局测试用简体中文驱动（`Locale('zh')` 加中文 `find.text` 目标）——CJK 字形本来就是方的，于是测试测量的是真实的生产布局。测试文件在头部注释中说明了这一点。
   - **默认的 800 x 600 测试视口是通过 `canSplitLayout` 的。** 任何在意此事的测试都必须固定一个明确的视口，否则它会悄悄开始走双栏路径。
4. **桌面上跨每个阈值实时缩放**，并对任何本不应滚动的窗格做软键盘检查。
